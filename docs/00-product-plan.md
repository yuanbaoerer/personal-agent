## 1. 产品定义

一个集成在聊天软件中的个人助手：主人始终面对同一个助手，内部由主 Agent 协调任务 Worker。助手可以在后台推进长任务，接收补充要求和取消指令，在必要时请求审批，并主动交付结果和提醒。

核心体验：**不切换多个 Agent 会话，也能同时安排几件事，并知道它们是否完成。**

术语以 [CONTEXT.md](../CONTEXT.md) 为准。业务 Task、一次 Assignment 和会改变外部状态的 Action 是三个不同概念。

## 2. 三条主流程

### 2.1 后台任务与持续对话

1. 主人发送资料：“整理这些出差材料，给我一份待办清单。”
2. 助手确认接单，建立任务；Worker 在独立上下文中工作。
3. 主人继续查询天气，或安排另一个资料任务；主对话保持可用。
4. 主人引用原消息：“改成周三出发”或“取消这项任务”，要求送到对应任务。
5. 结果回复原对话，包含完成内容与必要来源；内部步骤不逐条刷屏。

简单查询直接处理；耗时、多步骤、需要独立上下文的工作才交给 Worker。材料整理首版支持主人发送的文本，不以浏览器自动化或完整文件解析为前置条件。

### 2.2 审批后执行

1. 主人：“客厅灯调到 40%。”
2. 助手展示确定的设备、参数、来源、有效期和确认/取消操作。
3. 主人批准，程序执行器验证权限与动作版本，再调用工具。
4. 查询设备状态核对结果，回传成功、失败或“结果待核对”。
5. 改目标、改参数或取消任务会使尚未执行的旧审批失效；已经发生的动作单独报告。

控制灯是唯一计划中的外部写操作。开发先用 mock，真机接入是增强项；演示和报告必须明确两者区别。

### 2.3 持久提醒与记忆

- “明早 7:30 给我发天气简报”：确认时间、时区、内容及投递位置，创建持久提醒。
- “记住我出差喜欢靠窗”：保存显式偏好，可以在聊天中查看、修改和忘记。
- 主人关闭聊天客户端或 Agent 重启后，任务仍存在；提醒走聊天渠道发送。
- “内容已生成”“平台已接受消息”分别记录；没有平台回执时不声称用户已读。
- 提醒的授权只覆盖确认过的频率、内容和接收人，不能被扩展成任意外发消息。

## 3. 渠道优先级

默认先用**飞书自建应用机器人 + 主人私聊**完成 MVP。它是实施默认值，尚未完成账号、企业权限和发布条件验证；若主人日常使用其他渠道，可在第一周技术门槛前调整，只接一个首发渠道。

| 渠道 | 本轮核对的能力 | 本项目计划 |
| --- | --- | --- |
| 飞书 | 应用机器人支持消息接收/回复、交互卡片；群 Webhook 自定义机器人不能承担完整对话与回调 | 首发默认；HTTP 事件回调，聊天内审批及提醒 |
| 微信 | 腾讯 openclaw-weixin 提供扫码登录、长轮询收发消息及后端协议 | 后续适配；先验证账号可用性、授权续期、主动发送条件及长轮询宿主 |
| QQ | QQBot 渠道参考实现支持私聊、群聊、Webhook/WebSocket、定时推送和按钮审批 | 后续适配；按实际开放权限验证收发、回调和配额 |

腾讯的现成 OpenClaw 插件依赖其宿主，不能直接装进 Pi。后续应通过协议适配或独立消息网关接入，不为消息渠道引入第二套 Agent 调度系统。微信长轮询、QQ WebSocket 也不能直接等同于飞书 HTTP 回调的部署方式。

MVP 不接群聊，不自动绑定跨平台身份；后续群聊和私聊必须分开上下文。只有经过主人明确验证的账号绑定，才允许共享个人记忆与审批权。

## 4. MVP 必须交付

| 能力 | 最小范围 | 完成依据 |
| --- | --- | --- |
| 聊天入口 | 一个真实聊天渠道、一个已绑定主人 | 能接收、回复、主动通知，事件可去重 |
| 主 Agent | 一个逻辑 Router，统一回复；一个真实模型 | 长任务期间仍能处理新输入 |
| Worker | 同一实现按任务配置，最多两个并发，无嵌套派工 | 两项独立任务能并发，状态和上下文隔离 |
| 任务管理 | 目标、授权、版本、派工、状态、结果 | 可查状态、补充要求、取消、重启恢复 |
| 工具 | 一个真实只读工具（天气）+ mock 灯的读写 | 超时/输出上限明确，mock 可核对最终状态 |
| 审批 | 确定动作的确认、拒绝、过期与失效 | 不能跨用户、跨任务版本或重复消费 |
| 提醒 | 一次性天气简报，投递回原私聊 | 时间及投递状态落库，重启后继续 |
| 记忆 | 显式事实/偏好，结构化查询和管理 | 有来源，可修改/删除，无自动推断写入 |
| 证据 | 从第一周开始的关键回归、故障注入、报告 | 关键确定性用例全通过，真实模型评测单独统计 |

天气可用普通 HTTP Adapter，mock 灯用于 MCP Adapter 验证；无需为每个能力单独部署 MCP Server。每个适配是否走 MCP 都在报告中说明。

给当前主人回复、发送确认过的提醒走受限消息 Outbox；任意第三方接收人不在 MVP 范围。保存记忆、创建提醒也有状态变更，需基于主人明确指令展示内容并获得匹配的确认；执行程序记录授权依据。

## 5. 增强项与后续版本

完成核心验收后按顺序增加：

1. 本地 Connector + 一个真实灯：保持同一 Action 协议，补命令去重、结果核对和断线测试。
2. 只读日历与个人资料检索：以真实使用需求选择一项。
3. 一个简洁 Web 管理页：查看任务、审批历史、记忆和故障；日常对话留在聊天软件中。
4. 第二个聊天渠道：在共享核心逻辑前提下完成真实收发与审批测试。
5. 语义记忆检索、多模型路由、浏览器任务：先有基线和需求证据，再增加依赖。

首版不包含：多个平台同时首发、完整 Web 聊天客户端、任意 GUI 自动化、嵌套 Worker、自由互聊的 Agent 团队、独立 LLM Watchdog、多租户、模型训练，以及支付/门锁/密码管理器等高风险动作。

## 6. dsh-superagent 的借鉴范围

参考的是 deepseek-ai/dsh-superagent-prototype 的公开研究原型及其文档，不将文章中的所有探索视为已经实现。

| 参考设计 | 在本项目的取舍 |
| --- | --- |
| Source / Trigger / Channel | 统一聊天事件、定时触发与回信地址，保留平台验证和能力差异 |
| Ticket / Mandate | 业务 Task 有目标、完成条件与授权；与聊天会话、Pi 内部 task 分开 |
| Assignment / Worker Session | 一次派工有独立身份和版本；Worker 按任务配置，不先设多个固定人格 |
| Worker slots | 限并发，为人工补充、取消和状态查询保留响应能力 |
| Effects / Outbox | 状态变更和待投递工作先落库，提交后执行；失败可追踪和恢复 |
| 少占注意力 | 接单一次；完成、失败、需要决定时通知；进度留在任务记录中 |

本项目额外要求：所有写动作由程序约束；模型不能批准自己的动作。首版健康巡检用确定性超时、租约检查和预算上限，不增加一个常驻模型 Agent。

## 7. 交付门槛与待验证项

最先验证的四件事：飞书真实收发和卡片回调、Pi 多会话与恢复、Worker 忙碌时主对话响应、外部动作成功后记录中断的核对路径。

Cloudflare 是主选托管环境；单用户 DO 中承载多个独立会话是**待验证的部署设计**。前三个工作日执行技术门槛，失败按 [04](04-build-plan.md) 的同一规则选择替代方案，不在多个文档中设置不同期限。

所有规划能力目前都不是既有实现。现有 spike 只记录了本地 faux provider 的拦截与完成后重新打开数据库的结果。

## 9. 长期产品模式补充（2026-11-17，非 MVP）

产品长期允许用户选择「通用 / 编程 / 智能组织」快捷模式，但内部统一建模为 **WorkProfile（General/Coding/Research）× ExecutionStrategy（Direct/Delegated/Organization）**。Coding 决定领域能力与工具；智能组织决定任务依赖、分工、验收和经验沉淀，并非两个互斥的 Agent 实例。

全平台共享一个 Task/Approval/Memory Core；MVP 中单 Router、最多两个 Worker、禁止任意高权限操作的边界不变。详细类型、Coding 工作区隔离、Organization DAG、模式版本和分期实施见 [12 · Mode Architecture](12-mode-architecture.md)。原三条主流程仍是 v0.2 的验收范围，不能因规划扩展而视作已实现。
